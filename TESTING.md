# Pre-release end-to-end UI testing plan

## What “end to end” means here

An end-to-end test starts from the screen a user sees and operates the app through clicks, typing, navigation, and reloads. It uses the running mobile web app, API, and the same development or staging database. Multi-user tests open separate browser contexts so each user has independent cookies and local storage.

API and unit tests are useful supporting checks, but they do not replace these UI journeys.

## Test environments and accounts

- Use the existing local database during development and a staging database before release.
- Keep two ordinary members in the same commons: User A and User B.
- Add separate fixtures for a commons admin, store owner, applicant, and non-member when those journeys are automated.
- Prefix generated content with `E2E` and a unique run ID.
- Never point destructive or payment tests at production.
- Use Stripe test mode and test payment methods for payment journeys.

The local two-user fixtures are:

- `releaseclick1@test.cahootz.local`
- `releaseclick2@test.cahootz.local`

## Automated browser journeys

Community Pulse feedback (`community-pulse.spec.ts`): two isolated browser contexts sign in as `releaseclick1` and `releaseclick2`, then open the Community tab. Assert People → Circles → Pulse, inspect the basis, save independent answers, add/remove an explanation, reload, change an answer, and recover from a forced save failure without losing the last saved choice. Neither member sees the other's feedback, and an internal observation is absent. The journey rejects raw-text rendering warnings and checks the card and response controls at 320/375/414/768px widths. The fixture `apps/api/scripts/e2e-human-ai-feedback.ts` creates uniquely named `E2E-pulse-*` observations, verifies exactly two feedback rows and the database's immutable-wording guard, and deletes only its observations (feedback cascades). It refuses production and nonlocal databases. Requires migration `20261023000000_human_ai_feedback`. Optional `E2E_DATABASE_URL` directs the fixture to a disposable local database; use `E2E_API_BASE_URL` for a real API connected to that same database (the test forwards browser API requests to it). A third journey invokes the real publisher concurrently in an isolated, private E2E Commons, verifies exactly one observation, reads its basis through the UI, responds, reloads, and checks persistence. Cleanup removes that Commons’ observations, membership rows, wake records, and config. It tests publication but not Sage learning from feedback.

Start the API and mobile web app, then run:

```bash
pnpm -F @cahootz/api dev
pnpm -F @cahootz/mobile dev
pnpm test:e2e:mobile
```

Use `pnpm -F @cahootz/mobile test:e2e:headed` to watch Chrome perform the journey. Override the defaults with `E2E_BASE_URL`, `E2E_API_BASE_URL`, `E2E_USER_A_EMAIL`, `E2E_USER_B_EMAIL`, and `E2E_LOGIN_CODE`.

How the suite stays fast:

- **One sign-in per account per run.** A `setup` project (`e2e/auth.setup.ts`) signs both fixture accounts in through the real UI (journey 1) and saves each browser's storage to `apps/mobile/e2e/.auth/` (git-ignored). `newSignedInPage` starts every test's isolated context from that saved session instead of repeating the sign-in. Sign-out only clears the browser's own storage, so a test that signs out doesn't affect the saved session. If you run with `--no-deps`, delete `e2e/.auth/` first or the tests will reuse the last run's sessions.
- **Files run in parallel.** Three workers by default (`E2E_WORKERS=1` to run serially, e.g. on a slow machine). Tests inside one file still run in order. New specs must create uniquely named `E2E` content and must not depend on state another file changes. A spec that changes shared fixture-account state (for example "Show Sage decision trails" or welcome-lounge membership) must wrap its test body, cleanup included, in `withExclusiveAccountSetting("<state>", ...)` from `e2e/support/exclusive.ts`, so specs that touch the same state take turns instead of changing it under each other. `sage-decision-trail`, `agent-decision-trails`, `sage-decision-comments`, `sage-member-memory` and `sage-reply-parity` share the `sage-decision-trails` lock; all welcome-lounge membership journeys share `welcome-lounge-membership`; Sage journeys that create an introduction between the two shared accounts use `sage-introductions` because the product intentionally suppresses recent duplicate matches. Fixture cleanup must target only the alerts or records owned by its journey—never clear a shared account's whole inbox.
- **`pnpm -F @cahootz/mobile test:e2e:fast`** skips the `@sage` journeys (such as 15), which call a live model and are the slowest journeys (40s to 90s each). CI runs them nightly, not on pull requests.
- Video is recorded only when CI retries a failed test; traces and screenshots are still kept for every failure.

### Test tiers

Journeys run in three tiers, so a pull request gets an answer in about 10 minutes and the slow, nondeterministic journeys don't block merges:

| Tier | Tag | Runs | Time |
| --- | --- | --- | --- |
| Smoke | `@smoke` | Every pull request, plus every spec file the PR changed | ~10 min |
| Full deterministic | (untagged) | Every push to `main`, nightly, and manual runs | ~12 min, 4 shards |
| Live model | `@sage` | Nightly and manual runs only | ~8 min |

- **`@smoke`** marks the critical journeys a regression must never slip past: two-user sign-in and sign-out isolation, a post and comment between two users, Circle View for members and signed-out visitors, direct messages, emoji reactions, creating an event, inviting someone to a circle and their accepting, posting with retry, sending a proposal, a confirmed council vote, cart to checkout, paying a store by code, a receipt from History, wallet creation at sign-in, and a returning member's sign-in. Keep the set small (about 15 to 20 journeys). Add `@smoke` to a new journey only when it is a core path that has no smoke coverage yet, and remove it from one that has become redundant. A smoke journey must not wait on a `withExclusiveAccountSetting` lock or call a live model.
- **Untagged** journeys are deterministic. They run on a pull request only when it changes their spec file, and in full on `main` and nightly.
- **`@sage`** journeys call a live model and can answer differently from run to run. They report drift nightly rather than gate pull requests. Before merging a change to Sage behavior, run its `@sage` journeys locally, or start the workflow with **Run workflow**.
- A pull request that changes the E2E harness itself (`e2e/support/`, `e2e/auth.setup.ts`, `playwright.config.ts` or the workflow) runs every deterministic journey.

Run the tiers locally with `pnpm test:e2e:mobile:smoke`, `pnpm -F @cahootz/mobile test:e2e:fast` and `pnpm test:e2e:mobile` (everything). To run one spec, pass its file: `pnpm -F @cahootz/mobile exec playwright test e2e/events.spec.ts`.

**Flaky journeys.** A journey that fails and then passes with no code change is flaky. Fix it, or quarantine it the same day with `test.fixme()` and a comment that names the tracking issue. Don't raise retries or timeouts to hide it. CI retries a failed test once.

## Manual two-device release run

Automation on mobile web does not prove the native iOS and Android builds work. Before release, run the following with an iPhone and an Android device, or two real devices of the platforms you support:

1. Install a clean release-candidate build on both devices.
2. Sign in as User A on device 1 and User B on device 2.
3. Complete or defer profile setup and confirm each menu shows the correct account.
4. Have A create a post with text and an image.
5. Have B open the post, like it, comment, and share its link.
6. Confirm A receives the notification, opens the correct post, and sees B's actions.
7. Have A reply; confirm B receives and reads the reply.
8. Send a direct message in both directions and verify unread/read state.
9. Create a proposal with A and vote with B; verify totals on both devices.
10. Background and reopen both apps, switch networks, and repeat a refresh.
11. Sign A out; confirm B stays signed in and continues working.
12. Force-close and reopen; confirm the expected session state and persisted content.

Repeat the critical path once on mobile web in Chrome and Safari. Test the smallest supported phone, a current large phone, and any tablet layout planned for release.

## Exploratory test checklist

For every critical screen, also try:

- Empty fields, whitespace, minimum and maximum lengths, emoji, pasted text, and duplicate taps.
- Back navigation during a save, refresh during a request, app backgrounding, and reopening from a deep link.
- Slow network, temporary offline mode, API error, timeout, retry, and server recovery.
- Two users changing the same object close together.
- Direct URL access while signed out, signed in as the wrong role, and after logout.
- Empty, loading, success, validation, permission-denied, and unexpected-error states.

## Release gates

Do not release until all of these are true:

- Every P0 journey passes on staging.
- The automated Playwright suite passes twice consecutively from clean browser contexts.
- The manual two-device run passes on the release-candidate iOS and Android builds.
- No open bug can expose another user's private data, bypass a role check, lose money, duplicate a payment, or corrupt user content.
- Crash reporting, API error reporting, payment webhooks, backups, support contact, privacy policy, and account deletion have each been exercised once in staging.
- Every failed test has an owner and a release decision recorded; flaky tests are treated as failures until explained and fixed.

Record the build number, commit, date, devices, operating systems, tester, result, and links to failure artifacts for each release candidate.
